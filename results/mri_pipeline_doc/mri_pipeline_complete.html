01

Two paths, one feature contract

The single most important thing about this modality: there are two ways in, and only one of them works on a real patient.

ACDC ships an expert segmentation mask with every frame. That mask is the ground truth, the validation baseline, and the thing a real MRI will never have. So the modality has a second entry path that predicts the mask from the raw volume alone — and both paths emit the same eight-key feature dict, so everything downstream is identical for either.

Verified equivalence

ui_mri.features_from_masks was written to emit the same keys preprocess_patient emits, and reproduces its output byte-for-byte when handed the expert mask. The convergence is a checked property, not an intention.

Input

ACDC on disk

ACDC/database/{training,testing}/patientXXX/
├── Info.cfg                      ED / ES frame numbers, Group, Height, Weight, NbFrame
├── patientXXX_4d.nii.gz          full cine — NOT used, 4-D is explicitly rejected
├── patientXXX_frameNN.nii.gz     one cardiac phase, 3-D short-axis stack (X, Y, Z)
└── patientXXX_frameNN_gt.nii.gz  expert segmentation of that phase

Info.cfg parses to e.g. ED: 1, ES: 12, Group: DCM, Height: 184.0, Weight: 95.0, NbFrame: 30.

Label convention

Four constants defined once in mri_preprocessing.py and never redefined anywhere else in the project. The three foreground colours below are the ones the UI actually paints, lifted from ui_mri.overlay_mask_on_slice.

1 · LABEL_RV — right-ventricle cavity 2 · LABEL_MYOCARDIUM — LV wall 3 · LABEL_LV — left-ventricle cavity 0 · LABEL_BACKGROUND

Cohort: 150 patients — 100 in training/ (20 per pathology group) and 50 in testing/ (10 per group). The five groups are NOR (normal), DCM (dilated cardiomyopathy), HCM (hypertrophic cardiomyopathy), MINF (prior infarct with reduced function) and RV (abnormal right ventricle).

Upload Path B

Two .nii/.nii.gz files are required — ED and ES, because ejection fraction is a two-phase quantity. Three files are optional: an ED expert mask and an ES expert mask (only to unlock the predicted-vs-expert comparison), and an Info.cfg to auto-extract the pathology group and height/weight. The patient ID is regex-extracted from the filename (patient\d+), falling back to "upload".

03

Preprocessing Path A

src/mri_preprocessing.py — 452 lines, no ML dependency. One orchestrator, preprocess_patient(patient_dir), calling ten functions in a fixed order.

Loading

load_patient_info parses key: value line by line — ED/ES/NbFrame to int, Height/Weight to float, everything else (including Group) stays a string.

img = nib.load(path)
volume = img.get_fdata()                       # (X, Y, Z) float64
voxel_spacing_mm = img.header.get_zooms()[:3]  # 3-tuple, numpy.float32

load_nifti_volume is called four times per patient — ED volume, ED mask, ES volume, ES mask — and only the ED call's spacing is kept, since all four share the same geometry. Frame filenames are rebuilt from Info.cfg with zero-padding: f"{info['ED']:02d}" → patient001_frame01.nii.gz.

Slice selection

foreground_area_per_slice = np.sum(mask_volume > 0, axis=(0, 1))   # sum over X and Y
return int(np.argmax(foreground_area_per_slice))

The slice carrying the most heart tissue, typically mid-ventricle. Why not a fixed index: stack size and heart position both vary per patient — confirmed on patient001, whose slice 0 has zero foreground voxels. Computed independently for ED and ES.

ROI cropping — display only, never touches the numbers

rows, cols = np.where(mask_2d > 0)
top, bottom = rows.min(), rows.max() + 1
left, right = cols.min(), cols.max() + 1
margin = round(0.15 * max(bottom - top, right - left))   # PROPORTIONAL, not fixed px
# expand by margin, clamp to array bounds

The margin is a fraction of the box's own larger side because heart size varies enormously across the pathology groups — a dilated DCM heart against a small HCM one — and slice resolution varies across scanners. With zero foreground the function returns the full slice extent rather than raising; that fallback is mirrored later by the YOLO predictor.

union_bounding_boxes then takes ED's and ES's own tight boxes and crops both phases to their union. Without it each phase would be zoomed independently and a side-by-side comparison would be meaningless — the ventricle would look the same size in both. The image slice and its mask are transposed identically (volume[:, :, idx].T), so they stay registered.

Intensity → image

normalized = (slice_2d - min) / (max - min)
return (normalized * 255).astype(np.uint8)      # guard: all-zeros if max-min < 1e-8

MRI intensities are not bounded the way natural-image pixels are, so this min–max pass is required before any PNG encoding. encode_slice_to_base64_png then goes PIL.Image.fromarray(arr, mode="L") → in-memory PNG → base64.b64encode(...).decode("utf-8"). That string is what lands in Ollama's images field.

The one real bug found here

mode="L" requires uint8. Handing it a raw float64 slice makes PIL reinterpret each 8-byte float as 8 grayscale pixels, which renders as evenly spaced vertical stripes. Volumes and EF were always correct — they come from the mask — so only the display channel was wrong. Fixed in ui_mri.representative_ed by encoding raw_uint8.

Recorded in the code as a lesson: a len(b64) > 0 assertion passes happily on a garbage PNG. Look at rendered images; don't just assert they are non-empty.

Numeric features — computed on the full, uncropped 3-D mask

voxel_volume_mm3 = sx · sy · sz
volume_ml(label) = count(mask == label) · voxel_volume_mm3 / 1000     for label ∈ {1 RV, 2 Myo, 3 LV}

EF% = (V_ED − V_ES) / V_ED · 100                                      None if V_ED ≤ 0

Two implementation details carry weight here. The float(...) casts on each spacing component are not redundant: nibabel returns numpy.float32, and under NumPy's promotion rules python_float * float32 → float32, which is not JSON-serializable — it broke save_contribution until fixed. And cropping is never applied at this step: clinical EF is a whole-ventricle quantity.

04

The learned path Path B

Path A's ejection fraction depends on ACDC's expert mask. Without one, lv_ejection_fraction_pct is None, detect_flags_mri short-circuits, and the MRI agent produces nothing at all. Path B replaces that mask with a predicted one — and unblocks the whole chain without a single change to the agent.

The shared split, computed once

build_train_val_test_split(acdc_root, val_fraction=0.2, seed=42):

  • test = ACDC's own testing/ directory — 50 patients, 10 per group. Held out entirely; used only for final validation, never for training or model selection.
  • train / val = ACDC's own training/ directory (100 patients, 20/group), split 80/20 stratified per group (16 / 4 per group) with random.Random(42).

Reusing ACDC's own train/test directory boundary rather than inventing one is more defensible in the report and is already exactly patient-disjoint and group-balanced by construction — verified directly as 20/group and 10/group. This one split is reused by all three models, so they cannot drift apart.

Why the U-Net trains on jittered boxes

bbox = manifest ground-truth box
if jitter:  bbox = _jitter_bbox(bbox, scale ∈ U(0.85, 1.15), translate ∈ ±10% of the box side)
image_crop = image[top:bottom, left:right]  → resize 256×256 BILINEAR → /255 → (1,256,256) float32
mask_crop  = mask [top:bottom, left:right]  → resize 256×256 NEAREST  → (256,256) int64

Jitter is train-split only. At inference the box comes from YOLO, which is imprecise; training the segmenter on a perfectly tight ground-truth box would fit it to an input distribution it never sees in production. val and test use the exact unjittered box — a clean baseline for model selection — while the true end-to-end number, against a real YOLO's boxes, is measured separately in stage 06.

Why the classifier is fed the predicted mask

Its input is 5 channels: the grayscale image (1) plus the one-hot mask (4: background / RV / myocardium / LV). Deliberately the predicted mask, not ACDC's expert one — the same reasoning as the jitter. At deployment the classifier only ever sees the U-Net's output, so training it on cleaner data than it will ever receive would be self-deception. cache_predicted_masks runs the trained YOLO+U-Net chain once per slice and caches the result as .npy; otherwise every epoch would pay a full segmentation forward pass.

Augmentation — and the one transform deliberately not used

Applied identically to image and mask, train split only: rotation ±15°, translation ±10 %, zoom 0.90–1.10 (TF.affine, BILINEAR for the image, NEAREST for the mask); then with p = 0.8 brightness ×U(0.8, 1.2) and contrast ×U(0.8, 1.2) on the image alone; then with p = 0.5 additive Gaussian noise σ = 6, clipped to [0, 255]. No flips — the heart is not symmetric.

Per-slice training, per-patient validation

Every foreground slice is a training example inheriting its patient's group label, but per_patient_accuracy averages the softmax vectors over all of a patient's slices and only then takes the argmax. "This patient is likely class X" is the real deployment output; a slice-level accuracy corresponds to nothing clinically meaningful.

The inference chain

predicted_mask = _predict_mask_slice(...)
image → 256×256 /255 ;  mask → 256×256 NEAREST → one-hot(4) → transpose to (4, H, W)
input  = concat([image[None], mask_onehot]) → (1, 5, 256, 256)
probs  = softmax(classifier(input))
return {f"pathology_{cls}_probability": float(p) for cls, p in zip(PATHOLOGY_CLASSES, probs)}

Upload robustness — ui_mri.py

The pipeline assumes axis 2 is the short-axis slice stack. True for ACDC, not guaranteed for an arbitrary upload — and slicing the wrong plane produces a striped image and a garbage mask. The robust cue is voxel spacing: through-plane spacing is much larger than in-plane, e.g. 10 mm against 1.5 mm.

if max(sp) > 1.5 * min(sp):  axis = argmax(spacing)     # the through-plane axis
else:                        axis = argmin(shape)        # fallback: fewest slices
to_canonical → np.moveaxis(volume, axis, 2), spacing reordered to match
             → raises on 4-D input (a *_4d.nii.gz cine uploaded instead of a single phase)

The page then shows a slice-validity indicator that is anatomical, not merely "is there tissue":

labeled, ncomp = scipy.ndimage.label(pred_slice > 0)
largest_frac   = largest_component_size / total_foreground
ok = (coverage ≥ 1.0%) and (≥ 2 structures present) and (ncomp ≤ 8) and (largest_frac ≥ 0.35)

A real short-axis slice yields a compact mask — a myocardium ring plus an LV blob. A wrong-axis image fragments into many thin pieces even though "tissue" exists; that fragmentation is the striped-image signature.

05

The MRI agent

src/mri_agent.py — 467 lines. One entry point, generate_mri_contribution(...), in six steps. It produces structured findings, never a diagnosis: that is the Sep Agent's job.

1 · Learned features, opt-in

compute_pathology_classifier_features is a thin wrapper over predict_pathology_probabilities with a lazy import inside the function. That differs deliberately from the ECG agent's embedding wiring: a module-level import would force every importer of mri_agent — including mri_flag_validation.py, which needs only the pure threshold logic — to install ultralytics, segmentation_models_pytorch and torchvision just to import mri_agent.

It takes the raw, uncropped ED slice, not preprocess_patient's already-cropped display image: that crop derives from the expert mask (absent at deployment), and the classifier was itself trained on YOLO's own imperfect crops. It runs only when all four of raw_ed_slice_uint8 / yolo_model / unet_model / classifier_model are given, and its five outputs merge into the feature dict — so they automatically become valid evidence_ref keys.

2 · Deterministic decision

Pure threshold logic, no LLM, returning an MRIDecisionPlan(deterministic_flags, skip_llm_call, reason).

Class abbreviations are spelled out via _PATHOLOGY_CLASS_NAMES. This proactively applies a fix the ECG agent needed empirically: given the bare abbreviation "HYP", MedGemma glossed it as "hypokinesis" — a real but wrong clinical concept. Same failure mode, so the same guard.

4 · Prompt

A thin wrapper over the shared agent_common.build_generic_findings_prompt, with agent_role="an MRI analysis agent", modality_label="MRI", evidence_keys = list(feature_dict) + list(image_keys), and — unique to MRI — image_labels=image_keys. That last one exists because Ollama attaches no names to images; without it the model cannot know which attached image is which. It renders as:

The following images are attached, in this order:
- Image 1: short_axis_mid_ed

The scaffold enforces the project-wide contract verbatim — "You are ONE of several parallel agents (ECG, MRI, structured patient data) whose outputs will be combined by a separate aggregating component… Do NOT produce a diagnosis" — plus the exact JSON shape and two MRI-motivated rules: a finding that restates a listed feature must cite that feature's own key, not an image; and an image may only be cited for a visual observation no listed feature already captures.

5 · The call

images = [preprocessing_result["images"][k] for k in image_keys]
raw_response = llm_call(prompt, images=images)     # default: generate_report_medgemma

Ollama medgemma:4b, always with options={"num_ctx": 8192, "num_predict": 2048}. The explicit num_ctx is necessary: without it Ollama falls back to roughly 2–4k tokens regardless of MedGemma's real 131k capacity, and long prompts get cut off mid-JSON.

MedGemma is natively multimodal (SigLIP image encoder), so the same model serves ECG text-only and MRI with an image; only the prompt and the images argument differ. There is no second vision model. The Groq cloud backend cannot be used here — it is text-only and would not see the image, which is why the MRI page is MedGemma-only.

image_mode is "ed_only" or "ed_es", defaulting to "ed_only". Both work — validated on two patients, DCM and HCM, in both modes, valid JSON on the first attempt every time — but MedGemma's published evaluation is primarily single-image with multi-image described as experimental, and two samples do not justify overriding that caution.

6 · Parsing, and the correction that had to live in code

parse_findings_response strips a leading ```json fence (MedGemma wraps its JSON in one), then requires findings and flags_for_review, the five per-finding fields, evidence_ref ∈ valid_evidence_keys, and 0.0 ≤ confidence ≤ 1.0. Then:

if item["feature"] in numeric_evidence_keys:
    evidence_ref = item["feature"]          # override whatever the model cited
evidence_type = "image_region" if evidence_ref in image_evidence_keys else "numeric_feature"
Why the override exists

With an image attached, MedGemma cited the image as evidence_ref for every finding — including ones merely restating a number given in the text summary — and an explicit prompt rule did not fix it. So it is enforced in code: when a finding's own feature name exactly matches a known numeric key, that key wins. evidence_type is likewise derived here, from which registry the key came from, never trusted from the model. After the fix: 100 % correct evidence attribution on the validation patients.

On a parse failure the loop appends the error to the prompt — "Your previous response could not be parsed: … Return ONLY the corrected JSON object" — and retries, up to max_retries + 1 attempts (the UI passes 2); exhausting them re-raises.

What the agent hands over

AgentContribution(
  agent_id         = "mri",                    # this, not the class name, identifies the agent
  record_id        = patient_id,
  findings         = [Finding(feature, value, rationale, confidence, evidence_ref, evidence_type), …],
  flags_for_review = sorted(set(llm_flags) | set(decision.deterministic_flags)),   # UNION
  trace            = {"features_used": …, "model": "ollama:medgemma:4b",
                      "attempts": n, "image_mode": "ed_only"},
)

The skip branch returns the same shape with empty findings, trace["model"] = None, and a skipped_reason. Deterministic flags are merged whether or not the LLM ran — the guarantee is that a clinically notable ejection fraction never depends on the model noticing it.

07

Downstream

Sep Agent

The MRI contribution joins the ECG and patient-data ones in generate_sep_agent_decision(contributions, use_rag=…, use_cot=…, use_kg=…). The flag list is a deterministic union, never LLM-generated; every traceability entry must cite a real (agent_id, feature) pair present in the inputs or the response is rejected and retried.

Two pieces of that machinery are specifically MRI's:

  • Retrieval phrasing. _FLAG_QUERY_PHRASES maps each MRI flag to a clinical query — low_lv_ejection_fraction_suspected becomes "reduced left ventricular ejection fraction, systolic dysfunction". An A/B test showed that concatenating raw flag names retrieved dataset boilerplate instead of clinical criteria: the query, not just the knowledge base, was part of the problem.
  • The directional-consistency check is largely an MRI story. The two EF flags carry a directional block in clinical_kg.json (ventricle_key, measure_terms, forbidden_words, anchor_description), and the check rejects a summary stating an EF in the wrong direction relative to the flag actually raised.
The failure that forced the check

The Sep Agent once described patient001's markedly enlarged 295.5 mL LV end-diastolic volume as "low" — while every traceability entry correctly pointed at a real finding.

Traceability guarantees a cited finding is real, not that its characterization is correct. Those are two different guarantees, and only the first was enforced in code before this check existed.

Report and chat

report_pdf.generate_case_report_pdf renders the title, the synthetic-pairing disclaimer in red, the integrated summary, the flag union, the KG convergent-evidence section (only when use_kg ran), the traceability table with its standing caveat, then one findings section per agent with its demographic line, then any figures. Demographic context appears in the PDF only and is deliberately never fed to the Sep Agent's prompt — that agent combines already-interpreted findings and never needs raw demographics.

The MRI page stores the ED slice in st.session_state["mri_ed_b64"], which the chat page attaches — the reason chat uses local multimodal MedGemma rather than the text-only cloud backend. Chat only reads the case; it never writes a contribution, so it cannot corrupt the auditable case store.

09

Standing limitations

Stated plainly, because a limitation named in the report is worth more than one found by the reader.

LimitationWhat it costs
Only two phases are used. The 4-D cine is never analysed. No wall-motion or strain analysis; regional per-segment function is invisible. Only global chamber volumes are computed.
One representative slice reaches the vision model, chosen by maximum foreground area. The model's image-grounded observations describe a single mid-ventricular cross-section, not the stack.
The vision model is the ceiling on image grounding. MedGemma 4B is small. Its image findings stay qualitative. All calibrated numbers come from the mask (volumes, EF) or the classifier (probabilities) — never from the VLM. A stronger vision model is listed as future work.
The RV flag is weak — F1 0.562 on expert masks, 0.270 on predicted ones. Kept deliberately rather than tuned away, with the classifier's RV F1 0.80 as its complement.
Classifier accuracy is 0.62 over five classes, DCM ↔ MINF dominating the confusion. Useful signal, not a diagnosis — which is exactly why it enters the contribution as a probability finding plus a pattern_suspected flag, never as an assertion.
Ground-truth mapping caveat. ACDC group labels are read from each Info.cfg and are real; the primary paper's exact numeric criteria defining each group are not re-verified here.
image_mode="ed_es" works but stays non-default. MedGemma's evaluation is primarily single-image, and two validated samples do not justify overriding that.
Any ECG + MRI case is a synthetic pairing. PTB-XL and ACDC share no patients. Joint cases validate the architecture, not a real clinical presentation — and the exported PDF says so, in red.
